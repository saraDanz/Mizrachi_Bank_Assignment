# Requirements

Agreed scope for the user-management Web API, captured from the scoping interview.

This document is a **requirements contract**: what the system must do and why. It
deliberately contains no architecture, no component names and no code — those belong in
the design and in the source.

**Source specification.** A Web API exposing three operations — create user, delete user
by UserId, validate user by username and password — using a database repository pattern
and dependency injection, over an in-memory, file, or other database, with a user schema
of `UserId`, `UserName`, `UserPassword`.

---

## 1. Functional requirements

### 1.1 Create user

| ID | Requirement |
|---|---|
| FR-1.1 | Accepts a username and a password and creates a single user account. |
| FR-1.2 | The identifier is generated by the server. A client-supplied identifier is never honoured. |
| FR-1.3 | On success, returns the created identifier and username, and the location of the new resource. |
| FR-1.4 | The password is never returned, echoed, or included in any response. |
| FR-1.5 | Usernames are unique. Uniqueness is **case-insensitive**: `alice` and `Alice` cannot both exist. |
| FR-1.6 | Leading and trailing whitespace in a username is removed before uniqueness is evaluated. |
| FR-1.7 | A duplicate username is rejected as a conflict, distinct from a validation failure. |
| FR-1.8 | Under simultaneous requests for the same username, **exactly one** succeeds; the other is rejected as a conflict. Uniqueness must be guaranteed by the datastore, not by a prior check. |
| FR-1.9 | A password failing the policy in §1.5 is rejected as a validation failure, with the reason stated. |
| FR-1.10 | Creation is open to unauthenticated callers (self-registration). See §3.4. |

### 1.2 Delete user by UserId

| ID | Requirement |
|---|---|
| FR-2.1 | Deletes the account identified by the supplied identifier. |
| FR-2.2 | Requires an authenticated caller. An unauthenticated request is rejected as unauthorised. |
| FR-2.3 | The caller may delete **only their own account**. A request targeting any other identifier is refused as forbidden. |
| FR-2.4 | **Authorisation is evaluated before existence.** A caller therefore learns nothing about whether an identifier they do not own exists — every such request is refused identically, whether the account exists or not. |
| FR-2.5 | Deleting an account that does not exist — reachable only for the caller's own, already-deleted account — reports "not found". |
| FR-2.6 | Deletion is not idempotent by design: a repeat delete reports "not found" rather than success, so callers can distinguish the two. |
| FR-2.7 | Deletion is permanent (hard delete) in this scope. See §4.1. |

### 1.3 Validate user by username and password

| ID | Requirement |
|---|---|
| FR-3.1 | Accepts a username and a password and reports whether they identify a valid account. |
| FR-3.2 | Credentials are submitted in the request body. Credentials must never appear in a URL, query string, or path. |
| FR-3.3 | On success, returns the identifier and username of the validated account, and a credential the caller can use to authorise a subsequent delete. |
| FR-3.4 | On failure, returns "unauthorised". |
| FR-3.5 | **A wrong password and an unknown username are indistinguishable** — in status, in response body, and in response time. The endpoint must not become an oracle for which accounts exist. |
| FR-3.6 | Constant-time behaviour for unknown usernames is a requirement, not an optimisation: the work performed must not depend on whether the account was found. |
| FR-3.7 | Available to unauthenticated callers. |
| FR-3.8 | Rate limited. See NFR-2.4. |

### 1.4 Cross-cutting behaviour

| ID | Requirement |
|---|---|
| FR-4.1 | No response from any endpoint, on any path, contains a password in any form. |
| FR-4.2 | Errors are returned in a consistent, machine-readable format. |
| FR-4.3 | Error responses outside development must not disclose internal detail such as stack traces or datastore errors. |
| FR-4.4 | Every response carries a correlation identifier that can be matched to server-side log entries. |

### 1.5 Password policy

| ID | Requirement |
|---|---|
| FR-5.1 | Minimum length 12 characters. |
| FR-5.2 | Maximum length 128 characters — a bound on server work per request, not a storage limit. |
| FR-5.3 | All characters permitted, including spaces and non-ASCII. |
| FR-5.4 | **No composition rules** (no mandatory uppercase, digit, or symbol). |
| FR-5.5 | Passwords appearing on a list of commonly used passwords are rejected. |
| FR-5.6 | A password equal to the username is rejected. |
| FR-5.7 | Rejection states which rule failed, so the requirement is actionable by the caller. |

## 2. Non-functional requirements

| ID | Requirement |
|---|---|
| NFR-1.1 | Runs on a clean machine with no database software installed and no setup steps. |
| NFR-1.2 | Can also be run against a durable store, demonstrating that data survives a restart. |
| NFR-1.3 | The choice between stores is made by configuration, not by a code change. |
| NFR-1.4 | Invalid configuration fails at startup with a clear message, not at first request. |
| NFR-2.1 | Passwords are never stored in a recoverable form. Storage uses a salted, iterated, industry-standard password hashing function with per-user salt. |
| NFR-2.2 | Bespoke cryptographic code is avoided; a vetted, maintained implementation is used. |
| NFR-2.3 | Passwords are never written to logs. Usernames are never written to logs on a **failed** authentication, because that field may contain a mistyped near-miss credential and is personal data. |
| NFR-2.4 | Repeated authentication attempts are rate limited, to resist credential stuffing and brute force. |
| NFR-2.5 | Security-relevant events — account created, account deleted, authentication succeeded, authentication failed, authorisation refused — are recorded with enough context to reconstruct who did what and when. |
| NFR-2.6 | No secret, key, or credential is committed to source control. |
| NFR-2.7 | Interactive API documentation is not exposed outside development. |
| NFR-3.1 | Behaviour is covered by automated tests, including the security behaviours in FR-1.8, FR-3.5, FR-2.3 and FR-4.1. |
| NFR-3.2 | Where more than one datastore is supported, all of them are verified against the same behavioural test suite. |
| NFR-3.3 | Build, tests, and a dependency vulnerability check run in continuous integration. |
| NFR-3.4 | Source is published to a public source-control repository, as the specification requires. |

## 3. Decisions

### 3.1 UserId generation — **random GUID, server-generated**

Sequential integers are enumerable and would let one authorisation gap expose the whole
user table; they also leak business intelligence, since the difference between two ids
issued a week apart reveals customer growth rate.

*Noted:* an unguessable identifier is defence in depth, **not** an access control — which
is why FR-2.3 exists independently.

### 3.2 Username uniqueness — **enforced, case-insensitively, by the datastore; duplicates reported as a conflict**

Uniqueness is a precondition for FR-3.1 — validating "by username" is meaningless if a
username can match more than one account — and only the datastore can enforce it
atomically, since checking before inserting is a race (FR-1.8).

*Accepted trade-off:* reporting a conflict tells the caller that the account exists. This
is unavoidable for self-service registration — a user cannot be asked to choose a unique
name without being told when one is taken — and is mitigated only by rate limiting. The
asymmetry with FR-3.5 is deliberate: **validation never reveals existence; registration
unavoidably does.**

### 3.3 Password policy — **length-based, no composition rules, deny-list**

Composition rules narrow rather than widen the search space, because users satisfy them
predictably; screening against commonly used and breached passwords is what actually
removes the passwords attackers try first (NIST SP 800-63B).

*Noted:* password policy is among the lowest-leverage controls available here.
Multi-factor authentication and rate limiting prevent far more real account compromise
than any complexity rule.

### 3.4 Endpoint authentication and authorisation — **registration and validation open; deletion requires proof of ownership**

An unauthenticated destructive endpoint is not acceptable in a banking context, and
authentication alone would not fix it — any authenticated caller could still delete
another account, so an **ownership check** is required (FR-2.3), not merely a login.

*Why ownership rather than administrative roles:* an administrative role requires a role
attribute, and the specified schema is exactly three fields. Deviating from an explicit
written requirement was judged worse than scoping administrative deletion out.

*Known ambiguity:* "delete user by UserId" can be read as self-service or as an
administrative operation. This contract chooses self-service, for the reason above. If
the administrative reading was intended, this is a considered disagreement rather than an
oversight — see OQ-1.

## 4. Explicitly out of scope

Each item states why it is excluded and what production would require instead. This
section feeds the README.

### 4.1 Soft delete and data retention
**Excluded:** the specification asks for deletion, and a retention model is a larger
domain decision than this exercise supports.
**Production requires:** a bank cannot generally hard-delete a customer record.
Anti-money-laundering and know-your-customer obligations mandate multi-year retention,
which overrides an erasure request under data-protection law. Production would mark the
account inactive and anonymise personal data on the retention schedule, never remove the
row.

### 4.2 Dual control on deletion
**Excluded:** disproportionate for a three-endpoint exercise.
**Production requires:** removing a customer account should need a second approver, not a
single API call.

### 4.3 Administrative roles and permissions
**Excluded:** requires an attribute the specified three-field schema does not have (§3.4).
**Production requires:** role- or claim-based authorisation, with back-office account
management separated from customer self-service.

### 4.4 Password change and reset
**Excluded:** not in the specification.
**Production requires:** these flows are where the majority of real authentication
vulnerabilities occur — single-use expiring tokens, no user enumeration in the reset
path, re-authentication before change, and notification to the account holder. This is
the highest-risk area deliberately not built.

### 4.5 Multi-factor authentication
**Excluded:** out of scope.
**Production requires:** MFA on any account able to perform destructive operations. This
is the highest-value control absent from the current scope.

### 4.6 Account lockout
**Excluded deliberately, not overlooked.** Lockout is itself a denial-of-service vector:
an attacker who knows usernames can lock out every customer. Rate limiting (NFR-2.4) was
chosen instead.
**Production requires:** progressive delays, anomaly and impossible-travel detection, and
MFA — rather than a fixed failure threshold.

### 4.7 Credential lifecycle after validation
**Excluded:** short-lived credentials only, with no revocation.
**Production requires:** asymmetric signing with keys held in a managed vault or hardware
security module, short-lived access credentials with refresh, and a revocation path —
self-contained tokens cannot otherwise be withdrawn before expiry.

### 4.8 Federated identity
**Excluded:** issuing credentials directly is simpler for this exercise.
**Production requires:** an established identity provider rather than a bespoke
credential issuer.

### 4.9 Breached-password screening
**Excluded:** a representative deny-list is used instead of a full corpus (FR-5.5).
**Production requires:** screening against a breached-password service using a
privacy-preserving lookup, so that neither the password nor its full hash leaves the
bank's infrastructure, plus ongoing monitoring of existing accounts.

### 4.10 Encryption at rest, and a tamper-evident audit store
**Excluded:** the demonstration datastore is unencrypted, and audit events are written to
application logs (NFR-2.5).
**Production requires:** transparent database encryption or encrypted volumes, and an
append-only, tamper-evident audit store held separately from application logs, since
audit records must survive compromise of the application.

### 4.11 Operational telemetry
**Excluded:** logging only.
**Production requires:** vendor-neutral telemetry export, with automated redaction of
personal data.

### 4.12 Identifier strategy at scale
**Excluded:** not observable at this size.
**Production requires:** exposing an opaque public identifier while using a
storage-efficient internal key, since randomly ordered keys fragment indexes and inflate
write cost at volume.

### 4.13 Also excluded
API versioning; optimistic concurrency control; container packaging and deployment;
backup and disaster recovery; a user-listing or search endpoint (not requested, and it
would be an enumeration surface).

## 5. Open questions

| ID | Question | Status |
|---|---|---|
| OQ-1 | Was "delete user by UserId" intended as self-service or as an administrative operation? §3.4 assumes self-service. If administrative, the schema constraint must be relaxed to carry a role. | **Assumption made; unresolved with the specification's author.** |
| OQ-2 | Permitted username format — minimum and maximum length, and allowed character set — was never specified or discussed. Pending an answer, a conservative bound will be applied and documented. | **Open.** |
| OQ-3 | Should account creation also be rate limited? §3.2 relies on rate limiting to mitigate registration-based enumeration, but NFR-2.4 currently specifies it only for authentication. These are inconsistent. | **Open — likely yes.** |
| OQ-4 | Lifetime of the credential issued by FR-3.3 has not been agreed. | **Open; a short default will be applied.** |
| OQ-5 | Time budget for the exercise was never established, which is the main constraint on how much of §4 could be pulled into scope. | **Open.** |
